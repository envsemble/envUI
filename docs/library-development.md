# Extend the shared library

Read this page when a task authorizes changes inside envUI. First inspect [Customize and extend](customizing.md), public slots and existing variants. Product-specific wrappers can attach business meaning while shared components continue to own appearance.

## Public API and source ownership

Keep authored components in their existing family under `packages/ui/src`, named React exports in PascalCase files, and shared styles in `src/styles`. Add public exports to `index.ts`, `content.ts` or `rich-text.ts` according to the feature. Applications use those public entries and installed declarations, and may style a component's part classes and state attributes; avoid private component imports, component tokens and copied component CSS.

The site owns routes, page grids, specimen state and token measurement. Reusable UI behavior belongs in the package. Icons and brand wrappers are generated from their existing pinned inputs.

When a shared capability is missing, identify the required behavior and reusable API. Implement a variant, slot or component when library work is within scope. Otherwise report the concrete gap and preserve functioning product behavior. Keep routing, authorization, validation, preference and persistence in the application.

## Design tokens

The tokens are data: `packages/ui/tokens` holds them as DTCG 2025.10 `.tokens.json` files, with `envui.resolver.json` describing the themes. A token's path names its custom property, after the `--env-` prefix that every custom property of envUI takes: `color.fg.muted` is `--env-color-fg-muted`. A component's own custom properties take the prefix and its name, as `--env-card-padding` does, and never a token's name.

- `palette.tokens.json` is the primitive palette, generated by `npm run palette:generate` (`scripts/build/GeneratePalette.ts`) from a few seed colors per hue. Each grade is a band of WCAG luminance shared by every hue, so grades 40, 50 and 70 apart give 3:1, 4.5:1 and 7:1; `tests/Palette.test.mjs` checks it. A hue may add in-between grades in narrower bands, keyed with a hyphen for the point, such as gray's 2.75, `{palette.gray.2-75}`. The palette is internal and never becomes CSS.
- `base/color.tokens.json` holds the semantic roles, `color.{bg|fg|border}.{role}.{emphasis}[.{state}]`, as the light theme shows them, each an alias of a palette grade, with every hover and pressed state a token of its own. `color-scheme/dark.tokens.json` gives every role its dark grade.
- The `contrast` modifier's `high` context points roles at their high-contrast grades, which `base/contrast-high.tokens.json` and `color-scheme/dark-contrast-high.tokens.json` hold for each scheme. It builds as `[data-env-contrast='high']`, and under `prefers-contrast: more` unless a boundary sets `data-env-contrast='standard'`. Theme writes the attribute from its `contrast` prop on every boundary, nested ones and those around popups included, and none for `system`.
- The `scale` modifier's `compact` context, `scale/compact.tokens.json`, gives every size it changes its compact value: control and row heights, spacing, type, icons and corners. It builds as `[data-env-scale='compact']`, which Theme writes from its `scale` prop on every boundary. Components read only these tokens, never a multiplier, so a size that should follow the scale is a token. [Spacing & density](foundations/spacing.md) lists the values.
- Colors that no one role names, because a component takes another role per theme or a fixed color, are tokens whose role is the component, in the same grammar, such as `color.bg.list-item` and `color.fg.avatar`, which alias roles or the palette. Unlike a component token, a custom property a component declares for itself, they are public tokens like the roles.
- `removed-tokens.json` lists every custom property before 1.0 with what replaces it: `prefixed` the names that only take the prefix, `renamed` the names that changed beyond it, `aliases` the 0.7 alias tokens and `removed` the names with no counterpart. The build checks every replacement and writes `src/generated/token-migration.json`, which it copies into the codemods' rename map, where `v1-classes` reads it, and the migration guide. A token renamed or removed later goes there too.

`npm run tokens:build` runs Terrazzo (`packages/ui/terrazzo.config.mjs`), which lints the tokens and writes `src/styles/Tokens.css`, the internal typed module `src/generated/tokens.ts`, the token list `src/generated/tokens.json` and the migration map. Commit them with the token change; `npm run tokens:check` fails when they or the palette are stale, and the catalogue rebuilds them on every token edit. Every semantic color needs a dark value. Change colors by choosing another grade for a role, then run `npm run test:contrast`: the gate measures every declared pair in all four themes. A pair that leaves `tests/contrast/Pairs.ts` is listed there as dropped or renamed, with the reason; a pair a rename once led to can later be dropped or renamed onward in turn. `tests/contrast/DeclaredPairs.json` records what the gate requires of every pair, its kind and its minimum at each contrast, and the names of the dropped, renamed and relaxed pairs. Against it, the gate fails on a pair that disappears unexplained, on a pair held to less than before, by a weaker kind (`distinct` to `difference`, `text` to `non-text`), any switch between a ΔEOK kind and a ratio kind, a lower `minimum` or a contrast it is no longer measured in, and on a dropped, renamed or relaxed entry removed from `Pairs.ts`. A renamed pair is held to what its old name recorded, and, when it takes a name the snapshot already records, to that name's record as well. A deliberate relaxation is recorded in `relaxed` in `Pairs.ts`: the pair's name (the new one, for a renamed pair), the requirement it is held to now, as the gate's failure prints it, and the rationale. Each entry approves one loosening. Once the snapshot records it, it is spent: the entry stays as history, and loosening the pair again later, even back to a requirement relaxed before, needs a new entry with its own rationale. A new entry that relaxes nothing fails, so none can be recorded ahead of a loosening. After adding, dropping, renaming, tightening or relaxing a pair, `npm run test:contrast -- --update-snapshots` records the change; it writes nothing while the gate finds a problem. A missing snapshot is written only by a local run with `--update-snapshots`, never in CI, and only once the pairs pass against the base branches' copies, described below, and each `relaxed` entry is recorded by one of them or relaxes something one records. What DTCG can't express yet, such as font shorthands, is in `src/styles/TokensHandwritten.css`. A color the gate measures that a style sheet composes, such as a share of `currentColor`, is read from the style sheet itself: the declaration under a `/* contrast: name */` comment, so the formula lives in one place.

The snapshot is a file in the branch, so the gate also compares the pairs with the base branches' copies, which a branch's edits can't reach. The base is `ENVUI_CONTRAST_BASE`, any revision git knows. Unset, the bases are the merge-bases of `HEAD` with `origin/dev` and `origin/envui-1.0` that have the file, except the branch's own copies, which hold its edits: the branch it tracks, whatever its name, and its namesake on `origin`, so `envui-1.0` itself compares with `origin/dev` alone. The gate compares with every base and logs which. Against each, a pair held to less needs a `relaxed` entry that the base doesn't record, and every dropped, renamed or relaxed entry the base records must stay; so editing `DeclaredPairs.json` along with `Pairs.ts`, or deleting a recorded relaxation from both, still fails. An older base records less than a newer one, and a relaxation the newer one records is new since the older, so it approves the loosening there too. A base in the snapshot's first format, which named the pairs alone, holds them to nothing, but a pair it names still can't disappear unexplained. The gate reads only what the clone already has and never fetches: fetch the base branches first for up-to-date bases. Without git, those branches or the file at their merge-bases, it logs a note and compares with the working tree's snapshot alone, while an `ENVUI_CONTRAST_BASE` that git can't find, or where the file doesn't exist, fails. In CI, which runs for pull requests only, the `CI` job and the Verify workflow set `ENVUI_CONTRAST_BASE` to the first parent of the pull request's merge commit, the tip of the branch it merges into. In review, a change to `DeclaredPairs.json` shows in the diff as well.

A relaxation recorded on the branch but not yet on the base can be undone there: restore the pair, delete the entry from `relaxed` in `Pairs.ts`, restore the snapshot with `git checkout <base> -- tests/contrast/DeclaredPairs.json` and record the branch's other changes again with `npm run test:contrast -- --update-snapshots`. The base never recorded the entry, so nothing is lost. Once the base records a relaxation, it stays, and the pair is tightened again by a change to `Pairs.ts` alone.

## Component style sheets

Each component's CSS is a file of `src/styles` that puts its rules in `@layer env.components { … }` itself. `Base.css` declares the order of envUI's layers, `env.reset`, `env.tokens`, `env.base`, `env.components` and `env.utilities` (reserved for single-purpose classes), and imports the reset, Tokens.css and TokensHandwritten.css, the theme boundary's type, the surface, icon and motion rules and the font. `index.css`, built into `styles.css`, imports `Base.css` and then every component's style sheet, in the order that decides a tie between two of them. An application's CSS outside layers always wins, so a component needs no specificity hacks, such as `:where()` or a repeated class, to stay overridable; use them only to order rules within the components' layer. `tests/Layers.test.mjs` checks that the shipped style sheet is layered and that the library's custom properties take the prefix, and `tests/browser/CascadeLayers.spec.ts` that an application's rule wins. envUI's style sheets declare nothing `!important`; only a declaration that must beat a third-party style sheet outside layers would be.

A component's module imports `../styles/Base.css` and then its own style sheets, after its other imports, so the style sheets of the modules it builds on come first; the build points these imports at `dist/styles/`, through the package's `#styles/*` import, which resolves to an empty module in Node. A bundler keeps the style sheets of the modules an application keeps, in the order it evaluates them, so where rules of two style sheets tie on one element, the imports, not `index.css`, decide which comes first: import the one that comes first in `index.css` before your own, as ButtonGroup imports Button's, or give the rule a specificity that doesn't depend on the order, as Skeleton.css's take. `tests/StyleImports.test.mjs` checks the imports, the pairs known to tie and that a module rendering a class brings the style sheets that style it.

A component's style sheet draws no drop shadows: a sheet or toast separates by its fill, and a modal by its backdrop too. Rings drawn with `box-shadow` stay: focus rings and halos with no offset or blur, inset edges and selection bars, and a hairline one pixel beside a box. There are two exceptions. Avatar's: an avatar and an avatar group's count cast `--env-avatar-shadow`, 1 px down and 2 px soft, in a deeper shade of the surface below them, so stacked avatars part. And the frosted popups' (Popup.css): a popup on PopupSurface, the command palette, rich text suggestions and dialogs, which take the popup's fill solid, cast `--env-popup-shadow`, a small contact layer and a soft shadow in the text's color in light and a deeper shade of the page in dark, as their fill lets a little of what is behind through (`--env-popup-opacity`, over `--env-popup-blur`) with no edge; a tooltip casts a smaller `--env-tooltip-shadow` beside it, as its strong fill does (`--env-tooltip-opacity`); at high contrast, with reduced transparency and under forced colors the shadows are `none` and the popup, tooltip or dialog solid with its edge, `--env-elevation-{level}-border` on a popup or dialog. `tests/NoShadows.test.mjs` rejects any other shadow in the shipped style sheet, dev mode's and the catalogue's, any other custom property or token that is a shadow, an avatar shadow that grows, takes a color of its own or reaches another component, and a popup or tooltip shadow with a literal color, outside those popups, or that stays where they are solid.

Hover and focus inside never change a component's layout. A part that grew under the pointer could wrap the row it sits in and move out from under the pointer, which bunches it back, and the loop repeats. A part that moves or grows on hover does it with `translate`, `rotate` or `scale`, within room it keeps at rest, as AvatarGroup's spread does. `tests/StableHover.test.mjs` rejects a layout property in a `:hover` or `:focus-within` rule, also one a custom property set there carries into it.

Round corners are capped, so a tall element never keeps pill ends. Where a pill shape is meant, such as a button, a field, a badge or a navigation item, the radius is `var(--env-radius-full)`: half the tallest single-line control, the large control height or the touch height, whichever is more. One line tall, the browser scales the corners down to rounded ends; taller, as a button whose label wraps, a Combobox whose chips wrap or a toolbar whose controls wrap, the element keeps the same corners and becomes a rounded rectangle. A shape with small inner corners beside rounded ends, such as a button in a ButtonGroup, takes exactly half its own height instead, since corners that add up to more than the height make the browser scale down the small ones too. A radius of `50%`, `9999px` or `100vmax` stays only on parts that are always square, such as avatars, round icon buttons, dots and thumbs: `tests/Corners.test.mjs` fails on any other, and lists the square parts it allows.

Hairlines separate the items of one list, never regions. A Markdown rule, a table row and an accordion item take a hairline, `--env-color-border-muted`, across the full width of their container, edge to edge, never inset from its sides. A popup has none: its groups and separators part by space. Regions, such as a top bar, a footer, a sticky header, a tab bar or two panes, separate by space and background: a header that content scrolls beneath takes the muted fill, and two panes stand apart across a gap. Lines that say what something is stay: the outlines of fields, outline buttons and other controls, quote bars and keys; popups, tooltips and dialogs have none where they cast their shadow. In forced colors, where fills are gone, a part may keep a line where nothing else would set it apart.

A component's style sheet also holds its motion and its forced-colors rules:

- **Motion:** transitions and animations use the motion tokens. Fades always apply; movement, such as a press that settles or a popup that grows, only under `@media (prefers-reduced-motion: no-preference)`. Motion.css holds only the keyframes several components share.
- **Forced colors:** under `@media (forced-colors: active)` the system paints no fills or shadows, so a state that a fill or a shadow carries needs system colors: `Highlight` and `HighlightText` for a selected, chosen, current or highlighted item, with `forced-color-adjust: none` where text sits on the fill, an outline for a focus or a selection drawn as a shadow, and `GrayText` for an unavailable item. Colors that are content, such as swatches, keep theirs with `forced-color-adjust: none`. `tests/browser/ForcedColors.spec.ts` compares each state with its rest from computed styles; add a component with a new state to its page, `tests/fixture/ForcedColors.tsx`.

## One documentation source

Edit the relevant Markdown page under `docs/`; add a focused page when a new topic needs one. Register it in [the index](index.md) beneath its existing family. The index defines catalogue grouping and reading order, and page titles must match their entries. A component, pattern or foundation page is in the one-file structure: its summary, metadata and examples in frontmatter, its sections in a fixed order, its text as a lead and one-fact rules, examples as files and props generated from the TypeScript declarations. [Write a component page](component-pages.md) describes it, and the build fails on a page outside it. Other entries have a title, relative path and one-line purpose.

Keep examples, behavior and contracts in the Markdown page and its example files. The build generates the catalogue's internal TypeScript data from these files, and compiles the packaged documentation with the examples and props tables filled in; edit the maintained Markdown, examples and TSDoc, not generated files.

The setup skill contains setup steps only. Keep component details in their owning documentation page, and improve that page when integration reveals a gap rather than adding another guide.

## Part names

A component's part classes (`env-<component>-<part>`), state attributes (`data-*`) and color properties (`--env-<component>-<role>`, below) are public and versioned; its other component tokens, the custom properties it declares for itself such as `--env-card-padding`, are private. `npm run docs:parts` (`scripts/docs/GenerateParts.ts`) writes the contract to `docs/generated/parts.json`, which the docs' anatomy figures and dev mode read, and the package ships:

- It derives the classes from the source: the `env-*` literals in `className`, `classNames(…)`, a `class` property or a variable named for a class, with a class built from a value, such as `` `env-avatar-fallback-${fallback}` ``, expanded over the value's type. A class belongs to the exported component whose name, in kebab case, starts it: `env-card-header` to Card.
- It derives the states from the `data-*` attributes set in JSX on an element with a part class, with the values of the attribute's type, and from the `[data-*]` selectors the style sheets put on a part class, which add the states Base UI sets. A state's values are completed from what the component's code writes: an attribute in an object of props, such as `{ 'data-variant': variant }`, in its own module or one its classes occur in, and an element's `dataset` in a module it imports. Attributes named `data-env-ssr-*` are private and left out: server markup carries them only until a component reads its layout in the browser, such as PanelDock's while CSS stacks it before hydration. Use the prefix for such attributes alone; they may change in any release.
- A state that is on or off is present, as `''`, or absent, as Base UI renders its own, and CSS selects it as `[data-x]`: set it through `flag()` in `src/internal/flag.ts`. A state that takes values names them.
- State attributes keep one meaning each: `data-active` is the tab or panel that shows, `data-current` the destination of the page, beside `aria-current`, `data-selected` an option that is chosen and `data-highlighted` the keyboard or pointer cursor in a list, as Base UI's menus and lists set it. A pointer's drag takes one of four: `data-dragging` on a continuous control whose thumb moves, `data-moving` (`pointer` or `keyboard`) on an item being reordered, with `data-reordering` on its container, `data-resizing` on a handle and the region it resizes, and `data-drag-over` on a drop target under dragged files.
- `packages/ui/src/parts.json` holds what can't be derived: a one-line description of every part, by component, the `roots` of components whose root isn't `env-<name>`, the `shared` anatomy several components render, by class prefix, the classes no prefix `placed`, and each component's `colors`, its color properties with what each colors. A new part or color property needs its description there, and the generation fails without it, or when a listed property isn't registered in the style sheets or a registered one isn't listed.

Commit `docs/generated/parts.json` with the change. `npm run docs:check` fails while it is stale, and when a part, state attribute or value, or color property that the integration branch lists has gone without a `major` changeset of `@envsemble/envui` that names it: the class, the attribute, the property, or a value with its attribute. A rename or removal is a `major` change with a migration note. A part that moves to another component or shared group, or a state that comes to take any value, is not gone.

### Color properties and state layers

A component's colors are public color properties on its root, or on each item for a collection's `-item-` properties, which an application sets on one instance through `style` or CSS ([Customize and extend](customizing.md)):

- **Names:** `--env-<component>-<role>`, the component in kebab case, or its item's for the rows and destinations of a collection, such as `--env-list-item-container` and `--env-drawer-item-selected`. IconButton and a toolbar's toggles take Button's, Textarea TextField's.
- **Roles, few and the same everywhere:** `container`, the fill; `content`, the text and icons on it, which colors the state layers; `outline`, the edge; `icon`, an icon with a color of its own; `selected` and `selected-content`, what is chosen, current or on; `indicator`, a value's or a focus's mark, such as a slider's fill or a field's focused edge. Add a role only where these don't fit.
- **Registration:** each property is registered at the top of its component's style sheet as `@property --env-x-role { syntax: '*'; inherits: false; }`. It doesn't inherit, so it colors the one instance it is set on, and its initial value is the guaranteed-invalid one, so `var(--env-x-role, <default>)` falls back while it is unset. envUI never declares a color property; it reads it, with its default as the fallback. Parts that paint a root's color read a private property the root resolves for them, such as `--env-menu-item-icon-color`, since they can't read the root's own.
- **Defaults:** a variant or tone sets the private `--env-x-<role>-default`, which the rule that paints reads as the fallback, so the color property wins over every variant.
- **Default colors never change:** with no color property set, every state paints its semantic token, exactly as before the properties: each fill is `var(--env-x-custom-fill, <designed token>)` and each color `var(--env-x-content, <designed token>)`. `tests/browser/DefaultColors.spec.ts` compares every such component, in rest, hover, pressed and focus and in all four themes, with `tests/browser/DefaultColors.json`, recorded from the integration branch's style sheets.
- **States follow the colors an application sets:** `--env-x-custom-fill` is `var(--env-x-custom-layered, var(--env-x-custom-base))`, where the base is the container, or, while only the content is set, the default container through a content gate, `color-mix(in srgb, var(--env-x-content) 0%, <default container>)`, and the layered fill is `color-mix(in srgb, <base>, currentColor var(--env-x-layer))`: the content color over the container. A property unset is guaranteed-invalid, and so is everything that refers to it without a fallback, so the custom fill is invalid, and the designed token applies, until the container or the content is set. Hover, keyboard focus and press set the layer's opacity, `--env-x-layer`, from `--env-state-hover-opacity`, `--env-state-focus-opacity` and `--env-state-pressed-opacity`; at rest it is `initial`, so a custom fill is the plain container. A role whose designed state differs takes a multiple of the token and says why.
- **Contract:** list the properties under the component's `colors` in `packages/ui/src/parts.json`, and under a `### Colors` subsection of Anatomy on its page; `tests/DocumentationPages.test.mjs` checks the page names each. A new property is a `minor` change, a renamed or removed one `major`, with its old name in `removed-tokens.json` for the codemods.

The contrast gate measures the tokens, which are what envUI paints; the colors an application sets, and their layers, are its own to keep legible.

## Record the change

A change that people using envUI notice carries a changeset: a Markdown file in `.changeset/` that names the version bump and holds the changelog entry. Run `npm run changeset`, select `@envsemble/envui` and the bump, and write the entry as it should read in the changelog: what changed for someone using the package and, for a breaking change, how to migrate. Commit it with the change. Tests, tooling and catalogue-only changes need none.

- `major`: a breaking change, such as a removed or renamed component, prop, value, part class or state attribute.
- `minor`: a new component, prop, variant or token.
- `patch`: a fix that keeps the API.

Describe the pattern rather than the application that needed it: changesets, the changelog and this documentation name no application built on envUI, and `npm test` rejects them. Releases turn the changesets into the changelog; see `CONTRIBUTING.md` in the envUI repository.

## Verify

Check in three tiers at the envUI root, so a change is checked in seconds while it is made and in full only before it ships:

- `npm run check` after each change: lint, Stylelint and Prettier on the changed files, incremental types, the generated-file checks the change touches, the unit tests that need no build, and the browser specs related to the change in Chromium. Under a minute for a component, token or documentation change.
- `npm run check:affected` before committing a branch or merging it into the integration branch: the same, with the related specs' `@engines` tests in Firefox and WebKit, the builds the change needs and the unit tests that read them, and live development when the catalogue changed. A few minutes for a component change.
- `npm run verify`, which the Verify workflow runs on every pull request into `main`, and locally when asked: generated icons and tokens, lint, formatting, types, documentation links, package and site builds, isolated tarball consumers, SSR, browser acceptance in Chromium with the `@engines` tests in Firefox and WebKit, accessibility of every page, live development and the visual baseline.

Don't run the full tier, or the whole browser suite, after every change.

The first two compare the branch with its merge-base on the integration branch, `origin/envui-1.0` or else `origin/dev` (`--base <ref>` or `ENVUI_BASE` picks another), and add uncommitted and untracked files. `scripts/test/TestScope.ts` maps each changed file to its checks, and `npm run check -- --dry-run` prints the selection with the reason for each item:

- A library or fixture file runs the spec named after it, or after its folder: `Checkbox.tsx`, `Checkbox.css` and the fixture `Checkboxes.tsx` run `Checkbox.spec.ts`, and a file in `navigation/panel-dock/` runs `PanelDock.spec.ts`. `aliases` names the spec of a file whose name is not its spec's, such as `Theme.tsx` for `ThemePreference.spec.ts`.
- A token, theme or other widely shared file runs the contrast gate and a small shared set of specs; a file of the site runs the site's specs, and in the affected tier live development; `npm run verify` covers the rest.
- A spec runs itself, and a helper the specs that import it.
- A file that matches nothing runs no browser spec; the selection says so, and `npm run verify` covers it.
- An example file, a component or pattern page, the catalogue's stage or dev mode runs the layout check.
- Specs that need the library build, live development, which edits sources, and the layout check, which renders the whole catalogue, run in the affected tier.

Name a spec after the component it covers and test each behaviour once, in that spec. Tag a test `@engines` (`test('…', { tag: '@engines' }, …)`) when it depends on the engine: scrolling and sticky positioning, focus, pointer and touch, input methods, native forms, platform keys. Firefox and WebKit run only the tagged tests.

Write tests to stay fast: a unit test rather than a browser spec where the behavior allows, a computed-style or DOM assertion rather than a screenshot, a spec named after its component on its own fixture, and conditions rather than fixed sleeps.

- `npm run lint` runs ESLint over components, the site, tests and scripts. `npm run typecheck` checks the library, the site, the tests' types and fixture, and the scripts (`scripts/tsconfig.json`), which are TypeScript that Node runs as it is: they use only syntax Node can strip, and import with `.ts` extensions. It reports likely bugs and the Rules of Hooks, not style.
- `npm run lint:css` runs Stylelint over the library's and the site's CSS. Colors, stacking order (`z-index`) and font weights come from tokens, also in the `font` shorthand. Lengths that follow the text size use rem, and px is only for hairlines: border and outline widths, focus-ring offsets and shadow offsets, also as a `var()` fallback and in custom properties named for them, such as `--…-border-width`, `--…-ring-offset` or `--…-shadow`. em is only for typography that follows the element's own font size: `font`, `font-size`, `line-height`, `letter-spacing`, `word-spacing`, `text-indent` and underline offsets and thicknesses. Boxes, spacing and motion use rem, even when they sit in text; where a box must follow its own line of text, such as an icon as tall as the first line, disable the rule on that line with the reason. Library components take their sizes from tokens rather than literal rem values.
- `npm run format:check` checks Prettier formatting; `npm run format` applies it.

Where a rule does not fit one line, disable it on that line with the reason: a comment above `// eslint-disable-next-line rule`, or `/* stylelint-disable-next-line rule -- reason */`.

Style violations from before these rules are recorded per file and rule in `stylelint-suppressions.json` until the tokens replace them. A listed file fails once it has more violations of a rule than recorded, and a new file has none to spare. `npm test` also lints without the suppressions and requires every recorded count to equal the real one, since a count above it would leave room for new violations. After removing some, run `npm run lint:css -- --suppress` while `npm run lint:css` passes, so the lower counts are recorded; the file only shrinks.

The browser suite starts or reuses the site on port 8770 and the test fixture on 8766, with half the cores as workers (`ENVUI_WORKERS` sets a count or share); Firefox and WebKit take at most a third of them each, since they gain little from more and their slowest specs then run out of time. It reuses a server only when the server answers for this checkout; when another checkout or program holds a port, the suite takes ports of this checkout's own. To choose the ports, for example beside another checkout's tests, set them: `ENVUI_SITE_PORT=8832 ENVUI_FIXTURE_PORT=8833 npm run test:browser`. A run of the accessibility scan alone starts no server.

`npm run test:a11y` scans every page of the catalogue and the Docs in light, and the theme sample (`samplePages` in `tests/browser/helpers/CatalogueThemes.ts`) in dark and both high-contrast themes too, with axe in Chromium, against WCAG 2.2 A and AA and axe’s best practices. Today’s violations are listed in `tests/accessibility/KnownViolations.json` by page, theme, rule and element. A violation not on the list fails, and so does a listed one that no longer occurs. It scans the hosted site, which it builds first with `npm run build:site`, and serves from `dist/site/` inside the browser, so no server, port or connection is involved: the development server, with each module a request of its own, could drop a page’s files when it restarted or the system ran short of sockets, and leave the page blank. After fixing violations, run `npm run test:a11y:update` and commit the shorter list; add to it only for a reviewed reason.

`tests/browser/LayoutCheck.spec.ts`, the layout check, opens every figure the component and pattern pages place on its own, on the catalogue's stage in the fixture (`?fixture=layout-check`), and runs dev mode's `layout.at()` at 22, 40, 60 and 80 rem, with the window at each width so open overlays are placed for it. It fails with each problem's width, rule, path and message, and attaches the readouts. A don't figure (`dont=`) shows a mistake on purpose and is left out. A problem an example has on purpose takes an allowance in the spec, for that example, rule and path only, with its reason; an allowance that matches nothing fails.

`npm run test:visual` compares the catalogue’s specimens and their forced interaction states in light (or a page’s first live example when it has no specimen), the theme sample in dark and high contrast, a few open lists, the template screens and a few density specimens with the screenshots in `tests/visual/snapshots`. The contrast gate measures colours in every theme, so the baseline takes the other themes on the sample only. It renders inside the Linux Playwright image in Docker, pinned by digest in `scripts/test/VisualTests.ts` and run as `linux/amd64`, with Linux dependencies in named volumes, so every machine draws the same pixels; after raising Playwright, add the new image’s digest there. Each page’s images must match its specimens exactly: a specimen that stops rendering leaves its image missing, an image no specimen takes is orphaned, and both fail. After an intended visual change, run `npm run test:visual:update` and review the changed images like code. It writes changed and missing images, and removes a page’s orphaned ones only once the page has rendered, so a failed update deletes nothing.

`npm run verify` needs Docker for the visual baseline and stops at the start when Docker is not running. It builds once and runs the static checks, builds and unit tests side by side; then the browser specs of every engine with the accessibility scan, in one Playwright run with the cores to themselves, since timing-sensitive specs fail when other work competes for them; then the visual baseline and live development. To run every other check, use `npm run verify:no-visual` or set `ENVUI_SKIP_VISUAL=1`; both end with a warning that no screenshot was compared, so the run does not count as verified.
