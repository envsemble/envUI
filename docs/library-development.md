# Extend the shared library

Read this page when a task authorizes changes inside envUI. First inspect [composition](foundations/composition.md), public slots and existing variants. Product-specific wrappers can attach business meaning while shared components continue to own appearance.

## Public API and source ownership

Keep authored components in their existing family under `packages/ui/src`, named React exports in PascalCase files, and shared styles in `src/styles`. Add public exports to `index.ts`, `content.ts` or `rich-text.ts` according to the feature. Applications use those public entries and installed declarations; avoid private component imports, private-DOM selectors and copied component CSS.

The catalogue owns routes, page grids, specimen state and token measurement. Reusable UI behavior belongs in the package. Icons and brand wrappers are generated from their existing pinned inputs.

When a shared capability is missing, identify the required behavior and reusable API. Implement a variant, slot or component when library work is within scope. Otherwise report the concrete gap and preserve functioning product behavior. Keep routing, authorization, validation, preference and persistence in the application.

## Design tokens

The tokens are data: `packages/ui/tokens` holds them as DTCG 2025.10 `.tokens.json` files, with `envui.resolver.json` describing the themes. A token's path names its custom property, after the `--env-` prefix that every custom property of envUI takes: `color.fg.muted` is `--env-color-fg-muted`. A component's own custom properties take the prefix and its name, as `--env-list-item-fill` does, and never a token's name.

- `palette.tokens.json` is the primitive palette, generated by `npm run palette:generate` (`scripts/GeneratePalette.mjs`) from a few seed colors per hue. Each grade is a band of WCAG luminance shared by every hue, so grades 40, 50 and 70 apart give 3:1, 4.5:1 and 7:1; `tests/Palette.test.mjs` checks it. The palette is internal and never becomes CSS.
- `base/color.tokens.json` holds the semantic roles, `color.{bg|fg|border}.{role}.{emphasis}[.{state}]`, as the light theme shows them, each an alias of a palette grade, with every hover and pressed state a token of its own. `color-scheme/dark.tokens.json` gives every role its dark grade.
- The `contrast` modifier's `high` context points roles at their high-contrast grades, which `base/contrast-high.tokens.json` and `color-scheme/dark-contrast-high.tokens.json` hold for each scheme. It builds as `[data-env-contrast='high']`, and under `prefers-contrast: more` unless a boundary sets `data-env-contrast='standard'`. Theme writes the attribute from its `contrast` prop on every boundary, nested ones and those around popups included, and none for `system`.
- The `scale` modifier's `compact` context, `scale/compact.tokens.json`, gives every size it changes its compact value: control and row heights, spacing, type, icons and corners. It builds as `[data-env-scale='compact']`, which Theme writes from its `scale` prop on every boundary. Components read only these tokens, never a multiplier, so a size that should follow the scale is a token. [Scale and density](foundations/scale.md) lists the values.
- Colors that no one role names, because a component takes another role per theme or a fixed color, are component tokens, such as `color.list-item.bg` and `color.avatar.bg`, which alias roles or the palette.
- `removed-tokens.json` lists every custom property before 1.0 with what replaces it: `prefixed` the names that only take the prefix, `renamed` the names that changed beyond it, `aliases` the 0.7 alias tokens and `removed` the names with no counterpart. The build checks every replacement and writes `src/generated/token-migration.json`, which it copies into the codemods' rename map, where `v1-classes` reads it, and the migration guide. A token renamed or removed later goes there too.

`npm run tokens:build` runs Terrazzo (`packages/ui/terrazzo.config.mjs`), which lints the tokens and writes `src/styles/Tokens.css`, the internal typed module `src/generated/tokens.ts`, the token list `src/generated/tokens.json` and the migration map. Commit them with the token change; `npm run tokens:check` fails when they or the palette are stale, and the catalogue rebuilds them on every token edit. Every semantic color needs a dark value. Change colors by choosing another grade for a role, then run `npm run test:contrast`: the gate measures every declared pair in all four themes. A pair that leaves `tests/contrast/Pairs.ts` is listed there as dropped or renamed, with the reason; a pair a rename once led to can later be dropped or renamed onward in turn. `tests/contrast/DeclaredPairs.json` records what the gate requires of every pair, its kind and its minimum at each contrast, and the names of the dropped, renamed and relaxed pairs. Against it, the gate fails on a pair that disappears unexplained, on a pair held to less than before, by a weaker kind (`distinct` to `difference`, `text` to `non-text`), any switch between a ΔEOK kind and a ratio kind, a lower `minimum` or a contrast it is no longer measured in, and on a dropped, renamed or relaxed entry removed from `Pairs.ts`. A renamed pair is held to what its old name recorded, and, when it takes a name the snapshot already records, to that name's record as well. A deliberate relaxation is recorded in `relaxed` in `Pairs.ts`: the pair's name (the new one, for a renamed pair), the requirement it is held to now, as the gate's failure prints it, and the rationale. Each entry approves one loosening. Once the snapshot records it, it is spent: the entry stays as history, and loosening the pair again later, even back to a requirement relaxed before, needs a new entry with its own rationale. A new entry that relaxes nothing fails, so none can be recorded ahead of a loosening. After adding, dropping, renaming, tightening or relaxing a pair, `npm run test:contrast -- --update-snapshots` records the change; it writes nothing while the gate finds a problem. A missing snapshot is written only by a local run with `--update-snapshots`, never in CI, and only once the pairs pass against the base branches' copies, described below, and each `relaxed` entry is recorded by one of them or relaxes something one records. What DTCG can't express yet, such as font shorthands, is in `src/styles/TokensHandwritten.css`.

The snapshot is a file in the branch, so the gate also compares the pairs with the base branches' copies, which a branch's edits can't reach. The base is `ENVUI_CONTRAST_BASE`, any revision git knows. Unset, the bases are the merge-bases of `HEAD` with `origin/dev` and `origin/envui-1.0` that have the file, except the branch's own copies, which hold its edits: the branch it tracks, whatever its name, and its namesake on `origin`, so `envui-1.0` itself compares with `origin/dev` alone. The gate compares with every base and logs which. Against each, a pair held to less needs a `relaxed` entry that the base doesn't record, and every dropped, renamed or relaxed entry the base records must stay; so editing `DeclaredPairs.json` along with `Pairs.ts`, or deleting a recorded relaxation from both, still fails. An older base records less than a newer one, and a relaxation the newer one records is new since the older, so it approves the loosening there too. A base in the snapshot's first format, which named the pairs alone, holds them to nothing, but a pair it names still can't disappear unexplained. The gate reads only what the clone already has and never fetches: fetch the base branches first for up-to-date bases. Without git, those branches or the file at their merge-bases, it logs a note and compares with the working tree's snapshot alone, while an `ENVUI_CONTRAST_BASE` that git can't find, or where the file doesn't exist, fails. In CI, the browser job checks out two levels of history, and sets `ENVUI_CONTRAST_BASE` to the base when it has the snapshot: for a pull request, the first parent of its merge commit, the tip of the branch it merges into; for a push to `main`, the commit the push moved `main` from, which the checkout holds when the push added one commit, as a merge or squash does. A base from before the snapshot, a force-push, a push that creates the branch and one that brought several commits set none, with a notice, and the gate then compares with the checkout's snapshot alone; the pull request into `main` has already compared with its base. In review, a change to `DeclaredPairs.json` shows in the diff as well.

A relaxation recorded on the branch but not yet on the base can be undone there: restore the pair, delete the entry from `relaxed` in `Pairs.ts`, restore the snapshot with `git checkout <base> -- tests/contrast/DeclaredPairs.json` and record the branch's other changes again with `npm run test:contrast -- --update-snapshots`. The base never recorded the entry, so nothing is lost. Once the base records a relaxation, it stays, and the pair is tightened again by a change to `Pairs.ts` alone.

## Component style sheets

Each component's CSS is a file of `src/styles`, which `index.css` imports into a cascade layer of `env`: `env.reset` for the box-sizing reset, `env.tokens` for Tokens.css and TokensHandwritten.css, `env.base` for the theme boundary's type, and `env.components` for the components; `env.utilities` is reserved for single-purpose classes. An application's CSS outside layers always wins, so a component needs no specificity hacks, such as `:where()` or a repeated class, to stay overridable; use them only to order rules within the components' layer. `tests/Layers.test.mjs` checks that the shipped style sheet is layered and that the library's custom properties take the prefix, and `tests/browser/CascadeLayers.spec.ts` that an application's rule wins. envUI's style sheets declare nothing `!important`; only a declaration that must beat a third-party style sheet outside layers would be.

A component's style sheet also holds its motion and its forced-colors rules:

- **Motion:** transitions and animations use the motion tokens. Fades always apply; movement, such as a press that settles or a popup that grows, only under `@media (prefers-reduced-motion: no-preference)`. Motion.css holds only the keyframes several components share.
- **Forced colors:** under `@media (forced-colors: active)` the system paints no fills or shadows, so a state that a fill or a shadow carries needs system colors: `Highlight` and `HighlightText` for a selected, chosen, current or highlighted item, with `forced-color-adjust: none` where text sits on the fill, an outline for a focus or a selection drawn as a shadow, and `GrayText` for an unavailable item. Colors that are content, such as swatches, keep theirs with `forced-color-adjust: none`. `tests/browser/ForcedColors.spec.ts` compares each state with its rest from computed styles; add a component with a new state to its page, `tests/fixture/forced-colors.tsx`.

## One documentation source

Edit the relevant Markdown page under `docs/`; add a focused page when a new topic needs one. Register it in [the index](index.md) beneath its existing family. The index defines catalogue grouping and reading order, and page titles must match their entries. A component page carries its summary and metadata in frontmatter and follows the page template, with examples as files and props generated from the TypeScript declarations: [write a component page](component-pages.md) describes it, and how to convert a page that predates it. Other entries have a title, relative path and one-line purpose.

Keep examples, behavior and contracts in the Markdown page and its example files. The build generates the catalogue's internal TypeScript data from these files, and compiles the packaged documentation with the examples and props tables filled in; edit the maintained Markdown, examples and TSDoc, not generated files.

The skills contain routing and workflow instructions. Move conditional component details into their owning documentation page. Improve that page when integration reveals a gap rather than adding another guide.

## Agent files and skills

The files agents read come from the documentation's sources, as [For agents](agent-tooling.md) describes. `npm run docs:manifest` (`scripts/GenerateManifest.mjs`) writes `docs/generated/manifest.json` and `docs/generated/llms.txt` from the index, the pages' frontmatter, the example files, `docs/generated/props.json` and the token list. Commit them with the change: `npm run docs:check` and `npm test` fail while they are stale, so run it after `npm run docs:props` or `npm run tokens:build` too. The library build copies both to the package root, the manifest with the version, and writes `llms-full.txt` beside them.

The `envui` command is plain JavaScript in `packages/ui/bin`, run as it is from the installed package: `agents.mjs` renders the AGENTS.md index, `mcp.mjs` is the MCP server and `catalog.mjs` the lookups and ranking they share. It uses Node's own modules only, so installing envUI adds no dependency for it. `tests/Agents.test.mjs` holds the index to its 8 KB budget and calls every MCP tool over stdio.

The skills' source is `.agents/skills/`; each folder holds one `SKILL.md`, and the build copies them into the package's `skills/`. The agent plugin in `plugin/` carries a committed copy: run `npm run plugin:generate` after editing them and commit `plugin/skills` with the change, as [For agents](agent-tooling.md#how-a-release-updates-the-plugin) describes. Validate them with the available skill validator after editing them.

[For agents](agent-tooling.md) describes publishing the skills and the MCP server as a plugin.

## Record the change

A change that people using envUI notice carries a changeset: a Markdown file in `.changeset/` that names the version bump and holds the changelog entry. Run `npm run changeset`, select `@envsemble/envui` and the bump, and write the entry as it should read in the changelog: what changed for someone using the package and, for a breaking change, how to migrate. Commit it with the change. Tests, tooling and catalogue-only changes need none.

- `major`: a breaking change, such as a removed or renamed component, prop or value.
- `minor`: a new component, prop, variant or token.
- `patch`: a fix that keeps the API.

Describe the pattern rather than the application that needed it: changesets, the changelog and this documentation name no products, and `npm test` rejects them. Releases turn the changesets into the changelog; see `CONTRIBUTING.md` in the envUI repository.

## Verify

Check in three tiers at the envUI root, so a change is checked in seconds while it is made and in full only before it ships:

- `npm run check` after each change: lint, Stylelint and Prettier on the changed files, incremental types, the generated-file checks the change touches, the unit tests that need no build, and the browser specs related to the change in Chromium. Seconds: 10 to 20 for a component, token or documentation change.
- `npm run check:affected` before committing a branch or merging it into the integration branch: the same, with the related specs in Chromium, Firefox and WebKit, the builds the change needs and the unit tests that read them, and the accessibility scan and screenshots of the affected catalogue pages. About 2 minutes for a component change.
- `npm run verify` before a release and before merging into `dev` or `main`: generated icons and tokens, lint, formatting, types, documentation links, package and offline-catalogue builds, isolated tarball consumers, SSR, browser acceptance in every engine, accessibility of every page and the visual baseline. About 20 minutes.

Don't run the full tier, or the whole browser suite, after every change.

The first two compare the branch with its merge-base on the integration branch, `origin/envui-1.0` or else `origin/dev` (`--base <ref>` or `ENVUI_BASE` picks another), and add uncommitted and untracked files. `scripts/TestScope.mjs` maps each changed file to its checks, and `npm run check -- --dry-run` prints the selection with the reason for each item:

- A library module runs the specs about the components it exports, and in the affected tier the specs of the components that use it. A stylesheet stands for the components whose markup carries its classes. Specs are about the component their file name, their fixtures' names or their overrides name.
- A token, theme or other widely shared file runs the contrast gate and a small shared set of specs and pages; `npm run verify` covers the rest.
- A spec runs itself, a fixture the specs that load it, a helper the specs that import it. A documentation page's text waits for the affected tier, which scans and screenshots that page.
- Specs that need a build, and live development, which edits sources, run in the affected tier.

When the selection misses what a change affects, add the spec's subject to `overrides` in `scripts/TestScope.mjs`; `tests/TestScope.test.mjs` keeps the overrides pointing at specs and pages that exist.

Write tests to stay fast: a unit test rather than a browser spec where the behavior allows, a computed-style or DOM assertion rather than a screenshot, a spec named after its component on its own fixture, and conditions rather than fixed sleeps.

- `npm run lint` runs ESLint over components, the catalogue, tests and scripts. It reports likely bugs and the Rules of Hooks, not style.
- `npm run lint:css` runs Stylelint over the library's and the catalogue's CSS. Colors, stacking order (`z-index`) and font weights come from tokens, also in the `font` shorthand. Lengths that follow the text size use rem, and px is only for hairlines: border and outline widths, focus-ring offsets and shadow offsets, also as a `var()` fallback and in custom properties named for them, such as `--…-border-width`, `--…-ring-offset` or `--…-shadow`. em is only for typography that follows the element's own font size: `font`, `font-size`, `line-height`, `letter-spacing`, `word-spacing`, `text-indent` and underline offsets and thicknesses. Boxes, spacing and motion use rem, even when they sit in text; where a box must follow its own line of text, such as an icon as tall as the first line, disable the rule on that line with the reason. Library components take their sizes from tokens rather than literal rem values.
- `npm run format:check` checks Prettier formatting; `npm run format` applies it.

Where a rule does not fit one line, disable it on that line with the reason: a comment above `// eslint-disable-next-line rule`, or `/* stylelint-disable-next-line rule -- reason */`.

Style violations from before these rules are recorded per file and rule in `stylelint-suppressions.json` until the tokens replace them. A listed file fails once it has more violations of a rule than recorded, and a new file has none to spare. `npm test` also lints without the suppressions and requires every recorded count to equal the real one, since a count above it would leave room for new violations. After removing some, run `npm run lint:css -- --suppress` while `npm run lint:css` passes, so the lower counts are recorded; the file only shrinks.

The browser suite starts or reuses the catalogue on port 8770 and the test fixture on 8766, with half the cores as workers (`ENVUI_WORKERS` sets a count or share); Firefox and WebKit take at most a third of them each, since they gain little from more and their slowest specs then run out of time. It reuses a server only when the server answers for this checkout; when another checkout or program holds a port, the suite takes ports of this checkout's own. To choose the ports, for example beside another checkout's tests, set them: `ENVUI_CATALOGUE_PORT=8832 ENVUI_FIXTURE_PORT=8833 npm run test:browser`. A run of the accessibility scan alone starts no server.

`npm run test:a11y` scans every catalogue page, preview and usage, in both themes with axe in Chromium, against WCAG 2.2 A and AA and axe’s best practices. Today’s violations are listed in `tests/accessibility/KnownViolations.json` by page, theme, rule and element. A violation not on the list fails, and so does a listed one that no longer occurs. It scans the hosted catalogue, which it builds first with `npm run build:site`, and serves from `dist/site/` inside the browser, so no server, port or connection is involved: the development server, with each module a request of its own, could drop a page’s files when it restarted or the system ran short of sockets, and leave the page blank. After fixing violations, run `npm run test:a11y:update` and commit the shorter list; add to it only for a reviewed reason.

`npm run test:visual` compares the catalogue’s specimens, their forced interaction states and the density specimens in both themes with the screenshots in `tests/visual/snapshots`. It renders inside the Linux Playwright image in Docker, pinned by digest in `scripts/VisualTests.mjs` and run as `linux/amd64`, with Linux dependencies in named volumes, so every machine draws the same pixels; after raising Playwright, add the new image’s digest there. Each page’s images must match its specimens exactly: a specimen that stops rendering leaves its image missing, an image no specimen takes is orphaned, and both fail. After an intended visual change, run `npm run test:visual:update` and review the changed images like code. It writes changed and missing images, and removes a page’s orphaned ones only once the page has rendered, so a failed update deletes nothing.

`npm run verify` needs Docker for the visual baseline and stops at the start when Docker is not running. It builds once and runs the static checks, builds and unit tests side by side; then the browser specs of every engine with the accessibility scan, in one Playwright run with the cores to themselves, since timing-sensitive specs fail when other work competes for them; then the visual baseline and live development. To run every other check, use `npm run verify:no-visual` or set `ENVUI_SKIP_VISUAL=1`; both end with a warning that no screenshot was compared, so the run does not count as verified.

Exercise meaningful interaction changes in both themes, with keyboard focus and dismissal, native form submit/reset, narrow containers and enlarged text. Check portals, wrapping and local scrolling where affected. Inspect bundle boundaries when optional content or icon imports change.
